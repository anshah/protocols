Gossip Failure Detector Lab

Interactive companion to A Gossip-Style Failure Detection Service (van Renesse, Minsky, Hayden, 1998)

The problem

A group of processes needs to know which members are still alive. A central monitor is a single point of failure. Having every member ping every other member each period costs N messages per member per period, which stops scaling quickly.

The paper's answer: every member keeps a small table of heartbeat counters and, once per interval, sends that table to one randomly chosen member. Counters spread through the group like an epidemic. A member whose counter stops growing everywhere is presumed dead.

Traffic per member stays constant (one message per round, though each message grows with N), and the verdict is reached independently by every member with no coordinator.

State at each member

Each member holds a list with one row per member it knows about:

memberheartbeatlocal time of last increase A41t = 1038 B37t = 1031 C12t = 992

The last column comes from this member's own clock. Clocks are never compared between members, so no clock synchronization is needed. Only "how long ago did I last see this counter go up?" matters.

The algorithm in five steps

  1. Tick. Every T_gossip a member increments its own heartbeat and updates its own row.
  2. Gossip. It picks one member at random from its list and sends its whole list.
  3. Merge. On receipt, for each row keep the larger heartbeat. Whenever a row's heartbeat increases, record the current local time in that row.
  4. Suspect. If a row's heartbeat has not increased for T_fail, mark the member failed. The row stays in the list but is no longer passed on in gossip.
  5. Forget. After a further T_cleanup, delete the row. The wait matters: members reach the failed state at slightly different times, so if a row were deleted right away, a slower member that has not yet marked it failed could still gossip a stale copy and bring the dead member back with a fresh timer.

In this lab one "round" is 10 simulation ticks, and T_gossip is one round. Parameters below are therefore in rounds.

What the paper argues

  • The chance of a false accusation drops roughly exponentially as T_fail grows.
  • For a fixed accuracy, the needed T_fail grows only logarithmically with group size.
  • Detection stays reliable under substantial message loss and under many simultaneous crashes, if T_fail is chosen with them in mind.
  • On networks with several subnets, gossip should favor local peers so routers are not overloaded.

This lab is a simplified simulation for building intuition. Use the Playground's experiment runner to see these trends in numbers.

How to use this page

  • Guided steps walks through eight flows: the table, the merge rule, epidemic spread, crash detection, resurrection, false accusations, partitions and subnets.
  • Playground gives you every knob, a live cluster, charts, an event log and a batch experiment runner.
  • On any cluster, click a node to see the world from its point of view: green means fresh news, amber means ageing, red means marked failed.
  • Runs are deterministic for a given seed, so you can repeat an experiment exactly.
